# 历史候选的精确修复与审核（a9）

a9 包含历史缺口诊断、两种受限制的纯内存恢复接口，以及共同脱敏器的修复。它没有把普通 transcript 变成完整请求或任务成功记录；原来的质量、证据、授权和严格导出门槛继续生效。

## 诊断与来源

`diagnose` 现在识别既有历史工作区、工具正文省略、历史继承/分支/重放语义和原生协议字段缺口，返回对应所需材料。`unknown` 的归类修正本身不恢复正文。`historical_workspace_state_unverified` 另要求会话时点的工作区及文件排除规则；当前同名目录或当前 Git HEAD 不能证明历史状态。

对增长后的日志，调用方只有在原导入长度的完整行前缀与原始物理/展开摘要精确相等、会话/项目身份再次核验时，才能将该前缀作为原历史快照；不能把新追加的行混入旧样本后沿用旧审核。原始压缩来源变化不能用任意切片模拟历史前缀。

## Claude 原生请求元数据

`hooks/nous_training_claude_replay.py` 可在内存重建受支持版本的规范化请求，再核对原生日志摘要。完整使用、资源上限及未记录字段见 [TRAINING_CLAUDE_REPLAY.md](TRAINING_CLAUDE_REPLAY.md)。返回值可能包含敏感正文，只能逐项处理并释放；在持久化前必须独立完成脱敏。元数据报告只保留白名单字段、摘要、行号和计数。

调用方须先核验来源身份及授权，全程处理 `ReplayError`；`replay_resource_limit` 提前终止须标记扫描未完成。响应引用关系不是完整响应字节，也不是任务成功。不得通过删除未支持的字段来令原始请求假装完整。

## 单个 Write 输入与结果的恢复

`recover_anchored_write` 位于 `hooks/nous_training_anchor_recovery.py`。它只支持明确的 v1 Claude `Write`，输入恰为 `file_path` 和 `content`，并要求以下内容一致：

- 同一不可变原日志中的唯一调用与唯一对应结果；
- 经核验的备份清单、备份文件、当前文件及当前 Git HEAD blob 的字节摘要；
- 原工具的调用 ID、解析后位置、原候选省略标记、结果错误状态；
- 路径边界、非符号链接、静态排除及当前 Git 排除检查。

调用方负责先完成来源摘要与授权绑定，再重新脱敏并创建新版本 lineage。接口返回复制后的候选及安全收据；成功状态是 `recovered_observed_pair`，范围仅为两个内容块。原质量缺口及旧任务证据保留；调用方不得替换成成功审核。

共同脱敏器仅对已核查的原生结构化 Write 区分真实路径和正文。正文中提到 `.env` 等文档示例不自动等于这次写入的目标；真实目标仍受路径/Git 排除检查，正文仍经过凭据与个人信息清扫。

历史原路径已经迁移时，`scrub_record(..., _write_targets=...)` 接受调用方临时提供的精确绑定：调用 ID、原路径、原输入正文 SHA-256、当前目标及其项目。共同脱敏器再次验证目标字节、路径和排除规则。此参数是内部受信调用接口，不从 canonical JSON 字段读取，不授予来源授权，也不能取代上述原日志/备份/历史证据检查。一般 CLI 导入不会自动推断迁移映射。没有这类核验时继续保留省略；未知工具、额外参数和 shell 输入仍使用保守检查。

## 数据与证据的版本规则

原日志、缓存和已导出的旧候选应保留；修复结果写入新目录并记录父样本、源摘要、处理脚本与代码版本。修改正文后，旧摘要绑定的审核不能重新签成成功。已知凭据若有无标签重复，须在本批明确范围内补充值级清扫；原值留在内存，不写入审核报告。此类清扫证明已知值没有残留，不证明所有未知敏感内容都已排除。

只有结构完整、上下文和工具语义可核验、内容审核通过且具有准确版本绑定的独立任务结果证据，样本才可进入严格训练文件。一个独立短任务可以单独审核形成派生文本样本，但其资格不代表父轨迹合格；两个导出格式若来自同一个样本，不能按两项独立任务计数。

本地临时修复脚本、实际历史数据和本机凭据清扫列表均不属于最小发行包。包外验收报告应明确任务、平台/代码版本、源与样本摘要、执行结果及未通过原因。安装发行包不会自动启用采集，真实平台执行和训练效果需分别验收。
